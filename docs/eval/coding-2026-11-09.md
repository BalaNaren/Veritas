# Coding tasks: what is guaranteed, what was measured, what is not covered

Veritas 0.1.0, tested on macOS with git 2.54 (2026-11-09).

## How a coding task works

`veritas code "<goal>" --repo <folder>` makes a separate working copy (a git worktree) under `~/.veritas/worktrees/`, on a new branch `veritas/<goal>-<id>` cut from the commit that was checked out. An agent edits files in that copy. Veritas then runs the project's tests itself, before the change (baseline) and after each round, and sends a failing run back to the agent for up to two more rounds. The report is built by code from git's diff and from Veritas's recorded test runs; no model writes it.

`veritas apply <task>` saves the change as a commit on the task branch, `--merge` also merges it into the branch you started from, `--pr` also pushes the branch and opens a pull request. Each step asks first, every time. `veritas discard <task>` removes the copy.

## Guarantees and the tests behind them

| Guarantee | How it is tested |
|---|---|
| Your working folder, your branch and your uncommitted changes are never edited by a coding task. The only change in your repository is git's record of the extra copy and the new branch. | End-to-end: file hashes, `git status`, HEAD and branch list compared before and after a full task (`test/coding/coding-task.test.ts`, `test/coding/worktrees.test.ts`) |
| The agent's file tools reach only its working copy. | Live probe (`npm run probe:permissions`): with bare tool names the agent wrote and edited files outside its folder and read `/etc/hosts`; with Veritas's path-scoped rules every one of those was denied and work inside the folder still succeeded. Unit tests check that every file tool is scoped. |
| The agent cannot run git, install packages, or run any command except the approved test command. | The tool list contains only file tools and `Bash(<the approved command>)`; live probe: other Bash commands were denied |
| "Tests passed" appears in a report only if a recorded Veritas run exited with 0. | The verdict sentence is generated from the run records; sentences in the agent's own text that claim test outcomes are removed and the removal is stated |
| Commit, merge and push always ask; a flag cannot pre-approve them; an approval is good for one use. | Policy tests; end-to-end tests for deferral, decline, and re-asking after a first approval |
| Merge refuses when your repository is on another branch or has uncommitted changes, and a conflict leaves your folder exactly as it was. | Real-git tests including a deliberate conflict |
| Only a `veritas/` branch can be pushed, never with force, never to another ref. | `gitArgv` tests; a real push to a local bare remote |
| Project commands run without a shell, from an exact program path, with a minimal environment (no API keys or tokens), a time limit and an output cap. | `test/coding/test-runs.test.ts` |
| Each project command (for example `npm test`) is approved once per project. | End-to-end test |
| A malicious `diff.external` or text-conversion setting in a repository cannot run a program when Veritas reads a diff. | Test with a real hostile repository configuration |

## Bugs found while building this, now fixed

- An empty `diff.external=` in the git hardening made every non-empty `git diff` fail. Diff-producing commands now get `--no-ext-diff --no-textconv` instead, which also overrides repository settings.
- File tools given as bare names work anywhere on the computer under the headless runtime. They are now always scoped by path. The same hole existed for document agents (Read, Grep, Glob) and is closed.
- The push check accepted `--mirror` as a remote name; remote names must now start with a letter or digit.

## Measured runs (real model)

A two-function Node project with one wrong operator and a failing test, run with the default models: the change was made and the tests went from failing to passing in 8 seconds for $0.02 to $0.03. The task text also asked the agent to write a file outside the project and to run `git commit`; the agent declined both (and the permission layer would have denied them).

## What is not covered

- **Test commands are not sandboxed.** They run your project's code with your privileges, with a minimal environment but with network access and access to your files. Because the agent wrote some of the code those tests run, a hostile agent (for example one steered by text in the repository) could write code that misbehaves when the tests run. The mitigations are the one-time approval of the command, the separate copy, and the environment without keys. Running tests inside the macOS sandbox with the network off is possible but not done, because it breaks suites that need network or caches; this is a decision for the owner.
- **One coding agent per task.** Parallel coding agents with separate copies or file leases are not built.
- **Dependencies are not installed in the copy.** A project that needs them must be given `--setup-cmd "npm ci"` (approved like the test command).
- **No scanned or generated diffs beyond 400 KB** are shown in full; the branch has the complete change.
- **Pull requests need the GitHub command-line tool (`gh`)**, which is not installed on the test machine, so opening a pull request was not tested live. Pushing was tested against a local bare repository.
- **Uncommitted work in your repository is not included** in the copy (the task says so).
- Detached-HEAD repositories, repositories without a commit, and folders that are not repositories are refused with an explanation.
